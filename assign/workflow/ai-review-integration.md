# การต่อ AI วิเคราะห์ Portfolio สำหรับเดโม

วันที่: 1 พฤศจิกายน 2569 · branch `kan/backend`

## Flow

1. ผู้สมัครกรอกข้อมูล เลือก PDF และเลือกช่องยินยอมให้ส่งไฟล์ไป Gemini API ของ Google.
2. ระบบบันทึกใบสมัครในเบราว์เซอร์ แล้วส่ง PDF กับ requirement ของรอบรับสมัครไปยัง `/api/analyze-portfolio`.
3. Route ฝั่งเซิร์ฟเวอร์ตรวจชนิดไฟล์ ขนาดต่ำกว่า 45 MB และลายเซ็น PDF ก่อนส่งไป Gemini Generate Content API. API key อยู่เฉพาะฝั่งเซิร์ฟเวอร์.
4. AI ตอบผลตาม JSON schema: คะแนนเสนอแนะ สรุป หลักฐานตามเกณฑ์ จุดแข็ง ข้อมูลที่ยังขาด และข้อจำกัด. ระบบบันทึกผลใน localStorage และแสดงในหน้ารายละเอียด.
5. กรรมการตรวจผลและตัดสิน Approve/Reject เอง. AI ไม่เปลี่ยนสถานะผู้สมัครอัตโนมัติ.

## การตั้งค่า

คัดลอก `.env.example` เป็น `.env.local` แล้วกรอก `GEMINI_API_KEY`. ค่าเริ่มต้นของโมเดลคือ `gemini-3.5-flash`; เปลี่ยนด้วย `GEMINI_MODEL` ได้. Production ปิด AI ไว้โดยค่าเริ่มต้น เพราะต้นแบบยังไม่มี authentication และ rate limit. ไม่ควรเปิด endpoint สาธารณะด้วย API key จนกว่าจะเพิ่มการควบคุมการใช้งาน.

## ผลตรวจและข้อจำกัด

- `npm run typecheck` และ `npm run build` ผ่าน.
- ทดสอบ API จริงผ่าน `/api/analyze-portfolio` ด้วย PDF จำลองหนึ่งหน้าแล้วได้ HTTP 200 พร้อมคะแนน 65/100, หลักฐาน 4 เกณฑ์, จุดแข็ง 2 ข้อ และข้อมูลที่ยังขาด 2 ข้อ. ยังไม่ได้ทดสอบการแสดงผลผ่านเบราว์เซอร์ด้วย API จริง.
- โมเดล `gemini-2.5-flash` ตอบว่าไม่เปิดให้ผู้ใช้ใหม่; `gemini-3.8-flash` ตอบ 503 ในรอบทดสอบนี้. จึงใช้ `gemini-3.5-flash` เป็นค่าเริ่มต้น และ route ลองใหม่เมื่อพบ 500/503 ชั่วคราว.
- PDF อาจมีข้อมูลส่วนบุคคล ผู้สมัครต้องยินยอมแยกก่อนส่งไฟล์. ใช้ข้อมูลจำลองสำหรับการสาธิต.
- ควรเปิดหน้าส่งใบสมัครค้างไว้จน AI ทำงานเสร็จ; หากรีเฟรชระหว่างวิเคราะห์ ระบบจะแจ้งว่าคำขอถูกขัดจังหวะ เพราะแอปไม่เก็บไฟล์ไว้สำหรับส่งซ้ำ.
- คะแนนเป็นคำแนะนำจากโมเดลและอาจคลาดเคลื่อน ต้องให้กรรมการตรวจต้นฉบับก่อนตัดสิน.
